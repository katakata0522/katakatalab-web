CHAPTER 07｜開発運用とハマりどころ

ライブラリとフレームワークとは？「道具を借りる」か「枠組みに乗る」か

開発の記事を読むと「Reactはライブラリ」「Next.jsはフレームワーク」「素のJSで十分」といった表現が飛び交います。どちらも便利な再利用コードの集まりですが、設計の主導権がどちらにあるかが大きな違いです。

執筆：かたかた 公開：2026年11月28日 読了目安：約4分
ひとことで言うと

ライブラリは自分のコードから必要なときだけ呼び出す「道具箱」、フレームワークは決められた枠組みに沿って自分のコードを当てはめる「骨組み」です。

しくみの全体像

どちらも「よく使う機能をゼロから書き直さなくて済むようにまとめたコード集」ですが、最大の違いはどちらが主導権（制御）を握るかです。

ライブラリ（Library）は、日付計算や差分計算・QRコード生成など特定機能の部品集です。自分のプログラムから「ここだけお願い」と必要なタイミングで呼び出します。

フレームワーク（Framework）は、ルーティング・画面描画・データ取得などの全体構造とルールが先に決まっている土台です。開発者は決められた場所へ自分の処理をはめ込み、実行タイミングはフレームワーク側が管理します（これを制御の反転と呼びます）。

依存を増やす前に考えたいトレードオフ

便利なライブラリやフレームワークを使うと開発スピードは劇的に上がりますが、タダではありません。

  • メリット：車輪の再発明を防ぎ、実績のある書き方やセキュリティ対策を取り入れやすい。チームでも構造を共有しやすい。
  • コスト：バージョンアップへの追従、学習コスト、バンドルサイズ増加、脆弱性対応のメンテナンスが発生する。

「3行の標準JavaScriptで書ける計算のために巨大なライブラリを入れない」「複雑な状態管理や大規模UIにはフレームワークの力を借りる」という見極めが大切です。

最初は標準機能（Web標準）を知っておくと強い

フレームワークは数年で流行が移り変わりますが、その土台にあるHTML・CSS・DOM・Fetch・Web Cryptoなどのブラウザ標準機能は10年単位で通用します。KatakataLabでも、小さな計算ツールは素のHTML/CSS/JSで作ることで、数年放置してもビルドエラーで動かなくなるリスクを減らしています。

この言葉が会話に出てくるとき

「この機能、標準の Intl や crypto API だけで書けるからライブラリ要らないね」
外部依存を増やさずにブラウザ標準機能でシンプルに保つ判断です。

「画面遷移と状態が多いからフレームワークに乗せた方が保守しやすい」
規模が大きくなったときに手書き管理の破綻を防ぐための採用判断です。

勘違いしやすい点

  • 誤解1：フレームワークを使わない開発は時代遅れ。ページの目的に対して過剰な仕組みを入れないのは、表示速度と長期保守の面で立派な技術選定です。
  • 誤解2：人気ナンバーワンのフレームワークを選べば必ず速く作れる。小規模な静的ページでは、環境構築と設定だけで素のHTML作成より時間がかかることもあります。

まとめ

  • ライブラリ＝自分から呼ぶ部品箱、フレームワーク＝枠組み側が自分を呼ぶ土台。
  • 導入の速さだけでなく、更新保守・ファイル容量・学習コストも含めて選ぶ。
  • ブラウザ標準機能で足りる小さな道具は、依存を少なくするほど長持ちしやすい。

よくある質問

パッケージマネージャー（npmなど）とは何ですか？

ライブラリやフレームワークのバージョンを package.json で記録し、コマンドひとつで安全にインストール・更新してくれる管理ツールです。

Reactはライブラリですか、フレームワークですか？

React単体はUI描画に特化したライブラリとして位置づけられます。ルーティングやサーバー処理まで含んだNext.jsやRemixなどがフレームワークにあたります。
